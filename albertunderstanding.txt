===============================================================================
PART ONE - CODE QUALITY PROCESS
===============================================================================

1. THE SEGMENT IN ONE SENTENCE

Nothing reached main except through a reviewed pull request, and a continuous integration server
re-ran every check on a clean machine before any merge was allowed.


2. WHAT "CI" ACTUALLY MEANS

Continuous Integration. A server that runs your checks automatically so nobody has to remember to.

Concretely: the file .github/workflows/ci.yml tells GitHub Actions - GitHub's own build machines -
what to run. Open a pull request and GitHub starts a fresh Linux machine, clones the repository,
installs dependencies, and runs lint, tests, coverage and the build. The pull request page then
shows a green check or a red X. Nothing runs on your laptop, and nobody can forget to run the
tests before merging.

That is why it matters for this segment: the tests are not something the team claims to run. They
ran, on a clean machine, on every pull request, and the reports are attached to the run.


3. THE TRIGGER, EXACTLY

  on:
    push:
      branches: [main]
    pull_request:

Read that carefully, because it is easy to overstate. CI runs:

  - on every pull request, and
  - on pushes to main - which in practice means after a merge.

It does NOT run when you push a feature branch. Do not say "on every push"; a grader who opens
ci.yml sees `branches: [main]` immediately. The honest sentence is "every pull request, and again
on main after a merge", and it is a better sentence anyway, because thinking about the
post-merge run is more sophisticated than not.


4. THE TWO JOBS

Two jobs, named frontend and backend, both on ubuntu-latest. Neither declares `needs:`, so they
run in parallel - a failing frontend does not stop the backend from reporting. Frontend gets
Node 22; backend gets Java 17 Temurin.

The asymmetry is worth knowing. The frontend job is five explicit steps. The backend job is one
command that does four things.

  frontend:  npm ci  ->  npm run lint  ->  npm run test:coverage  ->  npm run build
             ->  npm audit --audit-level=high
  backend:   ./mvnw -B clean verify

What each covers:

  style                       frontend: oxlint          backend: Checkstyle, in Maven's
                                                                 validate phase
  tests with coverage         frontend: vitest, gated   backend: Surefire + JaCoCo, gated
  a production build          frontend: tsc -b &&       backend: compiles and packages the JAR
                                        vite build
  a dependency audit          frontend: npm audit       backend: nothing
  architectural rules         frontend: an import test  backend: ArchUnit, 5 tests

Two things to notice in that table:

  - "a production build" is not only bundling. `build` is `tsc -b && vite build`, so a TypeScript
    type error fails CI even though no test asserts types.
  - The dependency audit has no backend counterpart. This is why the slide says "between them they
    cover" - saying "both jobs run all of these" would be false.

Both jobs upload their reports as artifacts with `if: always()`, so the coverage reports exist
especially when the build fails.


5. THE TOOLS, IN PLAIN WORDS

You will be asked what these are. One sentence each.

  Checkstyle    A Java style checker. It reads the source and fails on violations of a written
                rule set (config/checkstyle/checkstyle.xml). It runs in Maven's `validate` phase,
                which is before compilation, so a style violation stops the build early.
                failOnViolation is true, and includeTestSourceDirectory is true - it lints the
                tests as well as the production code, which most student projects do not do.

  oxlint        The linter for the TypeScript side. Same role as Checkstyle: catches problems by
                reading the code rather than running it.

  JaCoCo        Measures how much of the Java code the tests actually reach, and produces the
                coverage report. It is also a gate: the build fails below the configured minimum.

  ArchUnit      A library that lets you write unit tests about architecture instead of behaviour.
                Our five tests assert which package is allowed to import which - for example that
                an entity never imports a framework. If someone adds a bad import, a test fails.

  MockMvc       Spring's way of calling a controller without starting a real server. Lets a test
                assert the HTTP status and JSON shape in milliseconds.

  npm audit     Checks the installed dependencies against a database of known vulnerabilities.
                Ours runs at --audit-level=high, so only high and critical findings fail.

The single most important sentence about all of them: none of them is advisory. Every one fails
the build rather than printing a warning.


6. THE PULL REQUEST TO SHOW - #37

Title: fix(battle): keep the resolver's status message out of the arena

  Was:  "Turn resolved. Arceus used Judgment!"
  Now:  "Arceus used Judgment!"

"Turn resolved." was an internal status string from the resolver, and it was being shown to the
player. The fix narrates a resolved move from its events alone, while a switch or an item keeps
its own message - because "Go! Garchomp!" and "Pikachu recovered 20 HP!" are the copy, not status
text. A regression test pins the behaviour so it cannot come back.

Why this one is worth showing: it is a real bug, with a real fix, and a test that prevents its
return. The rubric's top band asks for a pull request example. Have it open in a browser tab.

8. QUESTIONS YOU SHOULD EXPECT

Q: Why did the quality tooling land late?
A: Own the sequence. Checkstyle, JaCoCo and the CI gates came in with PR #40; PR #47 completed
   the use-case reorganisation and documentation. Saying so reads better than implying it was
   always there.

Q: What happens if CI fails?
A: The pull request shows a red X and the change is not merge-ready. The reports still upload, so
   you can read the coverage HTML from the failed run to see why.

Q: Does CI run on your machine?
A: No. GitHub Actions runs it on a fresh Linux machine, which is the point - it cannot depend on
   anything only installed locally.

3. WHAT IS COVERED

  - Entities: damage, healing caps, the type chart, party membership, the win condition, bracket
    progression.
  - Interactors: every use case, driven by stand-in data sources instead of real ones.
  - Adapters: JSON mappers in both directions, and controllers through MockMvc.
  - React: components, hooks, forms, and modal keyboard behaviour.
  - The dependency rule itself: ArchUnit in Java, an import test in TypeScript.


4. TESTING SOMETHING RANDOM - THE PART YOU WILL BE ASKED ABOUT

This is the most interesting thing in the segment, and it is not a random seed.

The problem: a battle turn rolls dice. It rolls for accuracy (did the move hit), for a critical
hit (1 in 24), and the opponent picks a move. If the code created its own randomness, a test
could not predict the outcome, and a test that cannot predict the outcome cannot assert anything.

The solution: the randomness is a constructor parameter.

  public BattleSimulator() { this(new Random()); }      // production
  public BattleSimulator(Random random) { ... }          // tests

Production calls the first constructor and gets real randomness. A test calls the second and
passes something that is not random at all:

  new BattleSimulator(new SequenceRandom(0.5, 0.5))

SequenceRandom is a small class in the test file that extends java.util.Random and overrides
nextDouble() to return the given values in order - 0.5, then 0.5.

Why 0.5 matters: the critical-hit check is `random.nextDouble() < 1.0/24`, and 1/24 is about
0.0417. A returned 0.5 is not less than 0.0417, so there is definitely no critical hit. Pass 0.0
instead and you force one. The test chooses.

The extra detail worth saying out loud: if the engine asks for more values than the test supplied,
SequenceRandom throws

  AssertionError("Simulator requested more random values than expected.")

So the test pins not only what each roll returns but how many rolls a turn is allowed to make. A
seed cannot do that. A seed gives you a repeatable sequence, but you still have to discover what
that sequence produces, and you cannot detect the engine quietly rolling an extra die.

The same pattern appears twice more: BooleanRandom for coin tosses, and IndexRandom for the
opponent's move choice. In the wider design, OpponentMoveSelector is an interface - a Strategy -
so a test can hand in a selector that always picks a chosen move.

If someone asks "is this dependency injection?" - yes. The collaborator is supplied from outside
rather than constructed inside, which is what makes the seam possible.


5. WHAT IS NOT TESTED, AND WHY

The rubric's top band explicitly asks for this, so do not skip it.

  - Live PokeAPI calls. Tests use recorded JSON so the suite does not fail when the network does.
    Adapter error paths are covered; a real outage is not.
  - The dev bearer token - the string the frontend sends to say who it is. It identifies a caller
    but is not cryptographically verified, so the suite makes no security claim about it.

If pressed on the weakest number: `app`, the command-line Main, is 1.3% covered. It is a
developer entry point that prints to stdout, not a shipped path; the web layer that users actually
reach is 94%. Say it before someone finds it.


6. ONE COMMAND REPRODUCES ALL OF IT

  .\scripts\verify.ps1

It runs the backend `clean verify` and then the frontend lint, coverage, build and audit. It fails
below the configured gates, so the numbers stay honest.

One practical warning if you run it on a fresh machine: it stops at the first failure under
`$ErrorActionPreference = "Stop"`, and the backend runs first, so with no Java installed it never
reaches the frontend at all. Java 17 Temurin has to be present.

A: Point at branch coverage instead - 76% backend, 77% frontend - and at the gate being enforced
   in CI rather than measured afterwards. Line coverage says a line ran; branch coverage says both
   sides of a decision ran.

Q: How do you test a random battle?
A: Section 4.

Q: Why is Main at 1%?
A: Section 5.

Q: Do the tests need a server or a network?
A: No. That is the "0" on the slide. Controllers are tested through MockMvc, and external data is
   recorded JSON.

PART THREE - ACCESSIBILITY REPORT
===============================================================================

1. THE SEGMENT IN ONE SENTENCE

We reviewed the app against the seven principles of Universal Design - not only disability
accommodations, but who can pick this up and use it at all - then named our target users and the
groups our own choices exclude.


2. WHAT THE RUBRIC ACTUALLY ASKS FOR

Out of 5. The Excellent band wants four things, and it is easy to misread the first:

  - All seven Universal Design principles in the MARKDOWN FILE. Not on the slide.
  - At least ONE principle discussed during the presentation.
  - Target users identified AND discussed in the presentation.
  - A group who may struggle identified, discussed using E3I terminology, in the presentation.

The slide carries six principles, which is five more than required. So do not add the seventh
for compliance. But the sentence "all seven are written up in docs/accessibility-report.md" is
what satisfies the first requirement, so SAY IT OUT LOUD - a grader cannot see a file you never
mention.

5/5 is "goes above and beyond in conveying the information outlined at the Excellent level."


3. WHERE THE REPORT LIVES AND WHAT IT CONTAINS

docs/accessibility-report.md, in the project repo. It was rewritten late - if you read an older
copy, the technical audit you remember is gone. Its current shape:

  - An opening framing it as a general review of how easily different people can understand,
    access and use the program, not only accommodations related to disability.
  - The seven principles, one short section each.
  - Marketing Audience - who we would market to if the intellectual-property rights were
    licensed.
  - Demographic Considerations - the barriers, with the E3I framing that these are mismatches
    created by design, technology and marketing choices rather than deficiencies in those groups.

Read it before presenting. The slide is built from it.


4. THE SIX PRINCIPLES ON THE SLIDE

  Equitable use            Guests and registered players reach the same core game; official,
                           custom and random Pokemon follow the same battle rules.
  Flexibility in use       Search or type-filter the catalog; hand-pick entrants or let random
                           selection fill them.
  Simple and intuitive     Menu, setup, simulation and result screens each explain one next
                           action at a time.
  Perceptible information  HP is a number and a bar and a colour; effectiveness is stated in
                           words, never colour alone.
  Tolerance for error      An item that would do nothing cannot be submitted at all - the invalid
                           target is disabled, and the server rejects it too.
  Low physical effort      Random filling, sticky selection controls, short menu paths, and no
                           dragging or timed input.

The seventh, Size and Space for Approach and Use, is in the report: responsive layouts, control
sizing, and the bracket being the highest-risk view on small screens.


5. WHAT IS ACTUALLY IMPLEMENTED

Each of these was checked in the source, not taken from the report:

  Skip link and a focusable main landmark          4 references
  Global :focus-visible ring                       8
  aria-pressed on toggle controls                 14
  prefers-reduced-motion                           4
  aria-live regions                                8 components - setup, forms, Pokedex,
                                                   tournament
  A real focus trap                                frontend/src/components/common/
                                                   useModalDialog.ts

useModalDialog.ts is the strongest single artifact in this segment, and it is 60 lines. It moves
focus into the dialog when it opens, closes on Escape but only when dismissal is allowed, wraps
Tab and Shift-Tab so focus cannot leave, and restores focus to whatever opened the dialog when it
unmounts. If anyone wants to see accessibility work rather than hear about it, open that file.


6. THE TWO REAL GAPS

Be the one who names them.

  - The battle message box is not an aria-live region. components/battle/ contains no live region
    at all, so a screen reader announces that a turn happened but not what it did. The fix is one
    attribute.
  - There is no aria-invalid or aria-errormessage anywhere. Form errors are visible text only, so
    they are not programmatically tied to their field.

Also true, and in the report: the tournament bracket has no linear text equivalent, and no
screen-reader session has been run.

Note on the slide: the card that admitted the aria-live gap was removed at Albert's request to
save space. The gap is still real. If a grader asks what a blind user cannot do, answer with the
message box - do not claim the app is complete.


7. TARGET USERS, AND WHO IS EXCLUDED

Target users: casual and experienced Pokemon fans, students, families, friend groups, and coding
clubs who enjoy matchups, collecting, customization, or learning from an interactive game system.

Excluded by our choices: English-only text discourages multilingual users; Pokemon terminology
excludes people unfamiliar with the franchise; and uncached data needs a modern browser and
reliable internet, which is a barrier on older devices and in lower-connectivity communities.

The E3I sentence, which must be said and not merely displayed: these are mismatches created by
design, technology and marketing choices, not deficiencies in those groups. Localization, offline
catalog support, broader onboarding and clearer privacy information would widen participation.

Do not cut that paragraph for time. It is the part that shows you understood the assignment. Cut
the implementation detail in section 5 instead.


8. QUESTIONS YOU SHOULD EXPECT

Q: What is E3I?
A: The course's embedded ethics, equity and inclusion material. The framing that matters here is
   that exclusion is a mismatch produced by design choices, not a deficiency in the excluded
   group.

Q: Can a blind person use this?
A: Partly, and be honest about the boundary. Keyboard operation, focus order and dialog semantics
   are real, and setup, forms and the catalog announce their state. But the battle message box is
   not announced, and the bracket has no text equivalent.

Q: Did you run a screen reader?
A: No. No automated screen-reader session exists and no manual session has been run. Roles and
   keyboard interaction are asserted by component tests; that is not the same thing.

Q: Is accessibility just about disability?
A: No, and the report is deliberately built the other way round. It starts from who can
   understand and use the program at all, which is why language, prior knowledge and connectivity
   sit alongside keyboard and screen-reader concerns.

THINGS NOT TO CLAIM
===============================================================================

  - Do not say CI runs "on every push". It runs on every pull request and on main after a merge.
  - Do not say party switching works from the user interface. The engine supports it and it is
    tested, but every shipped route into the arena builds a party of one.
  - Do not offer to demonstrate an item being refused. The bag disables the only valid target for
    a stat booster, so the action can never be submitted; the refusal exists in the interactor and
    over HTTP, but not on screen. Answer with the disabled control instead.
  - Do not describe the injected Random as a seed. Section 4 of Part Two.
  - Do not quote the older coverage baseline from docs/testing.md. It still publishes 255 tests,
    83.15% line and 68.09% branch, which predates PR #45. The current numbers are in Part Two.
