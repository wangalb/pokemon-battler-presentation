===============================================================================
PART ONE - THE SINGLE BATTLE USE CASE
===============================================================================

1. THE USE CASE IN ONE SENTENCE

A player picks their Pokemon and an opponent, then takes turns choosing a move, switching, or
using an item, and each turn is resolved by the Java backend until one side faints.

The three visible stages:

  Before   Two selection slots, each holding a chosen Pokemon or a question mark for random.
  During   The arena: both HP bars, a message box, and four actions - Fight, Bag, Pokemon, Run.
  After    A result panel naming the winner, with Battle again and Main menu.


2. THE ENDPOINT IS STATELESS, AND THAT IS THE DESIGN DECISION

There is one endpoint for the whole battle:

  POST /api/battles/turn

The server keeps no battle. The client sends the entire battle state with every request, and the
server sends back the new state. The request body is an envelope of three things:

  {
    battle: { playerParty, playerCurrentHp, playerActiveIndex,
              opponentParty, opponentCurrentHp, opponentActiveIndex },
    bag:    [ { name, kind, amount, quantity }, ... ],
    action: { type: "MOVE" | "SWITCH" | "ITEM", ... }
  }

BattleController.takeTurn rebuilds the domain object from that payload - `request.requireBattle()
.toBattle()` - switches on the action type, and calls one of three input boundaries: resolveTurn,
switchPokemon, useItem.

Why stateless is worth defending: the API is restart-safe, two battles cannot interfere, and the
tournament needs no server-side battle storage. The cost is that a browser refresh loses the
battle. That is the honest trade, and it is the answer to "why not keep the battle on the server?"

When an interactor rejects an action, the controller returns HTTP 400 with the message. That is
not an error screen - see section 9.


3. THE CLASSES, MATCHING THE UML

Frameworks and drivers:
  BattleArena.tsx                 the arena view; calls onMoveSelect, onItemUse, onSwitchPokemon
  services/battleApi.ts           builds the JSON envelope and does the fetch
  BattleController                the Spring controller; POST /api/battles/turn

Use case (package use_case.resolve_turn):
  ResolveTurnInputBoundary        the interface the controller depends on
  ResolveTurnInteractor           implements it; the turn algorithm lives here
  ResolveTurnInputData            battle + playerMoveName
  ResolveTurnOutputData           success + TurnResult + message

Entities (package entity):
  Battle                          the two parties, who is active, and current HP
  Pokemon, Move                   stats and move data
  BattleSimulator                 one attack: accuracy, crit, type, damage
  AttackResult                    hit, critical, damage, sameTypeAttackBonus, typeEffectiveness
  TurnAction                      one attacker's action, or a skipped one
  TurnResult                      the actions plus the resulting HP and outcome
  BattleSides                     turn rules shared by the three battle use cases
  MoveSelector / OpponentMoveSelector    the Strategy for choosing the opponent's move
  RandomOpponentMoveSelector      the shipped implementation

The dependency to point at: BattleController depends on ResolveTurnInputBoundary, not on
ResolveTurnInteractor. The interactor realizes the boundary, so the source-code arrow runs
opposite to the direction of the call. That is Dependency Inversion, and it is the one inverted
dependency to name if asked for an example.


4. ONE TURN, STEP BY STEP

This is ResolveTurnInteractor.resolve, in order:

  1. If the battle is already complete, reject with "Battle is already complete."
  2. Find the player's move by name on the active Pokemon, case-insensitively. If it is not there,
     reject with "Player does not know move: X."
  3. Ask the OpponentMoveSelector to choose the opponent's move.
  4. Decide who goes first (section 5).
  5. Resolve the first attack: simulate it, apply the damage to the defender, record a TurnAction.
  6. Before the second attack, check whether the battle ended or the second attacker just fainted.
     If either is true, record a SKIPPED action instead of attacking - a Pokemon that has just
     fainted does not get to answer.
  7. Send out the opponent's next Pokemon if theirs fainted (BattleSides.sendOutNextOpponent). The
     player chooses their own replacement, so only the opponent is automatic.
  8. Return success with a TurnResult built from the two actions.

Both attacks always produce a TurnAction - one of them may be a skipped one. That is why the
frontend can narrate a turn from the actions alone without needing to know the rules.


5. TURN ORDER, AND THE COIN FLIP

  boolean opponentActsFirst =
        opponent.getSpeed() > player.getSpeed()
     || (opponent.getSpeed() == player.getSpeed() && !tieBreaker.nextBoolean());

Higher Speed moves first. On an exact tie, a coin flip decides - and the coin is the injected
`Random tieBreaker`, so a test can force either order. Note the sense of it: `nextBoolean()`
returning true means the player goes first.

This is the smallest example of why the randomness is injected, and it is a good one to mention:
without the seam, the tie case would be untestable.


6. THE DAMAGE FORMULA

In BattleSimulator.simulateAttack:

  rawDamage = power
            * attacker.attack / defender.defense
            * sameTypeBonus            (1.5 if the move's type matches the attacker's)
            * typeMultiplier           (from the type chart; can be 0)
            * criticalMultiplier       (1.5 on a crit)

  damage = max(1, floor(rawDamage))

Constants: SAME_TYPE_ATTACK_BONUS = 1.5, CRITICAL_HIT_MULTIPLIER = 1.5,
CRITICAL_HIT_CHANCE = 1/24.

Order of checks inside the method:

  1. Validate: attack >= 0, defense > 0, power >= 0.
  2. Compute the type multiplier and the same-type bonus. Struggle is Normal for compatibility but
     always deals neutral damage.
  3. Accuracy roll. A miss returns immediately: hit = false, damage 0 - but the multipliers are
     still reported, so the UI can stay consistent.
  4. If the type multiplier is 0, or the move has no power, return a hit for 0 damage.
  5. Roll the crit, compute the damage, floor it, and never go below 1.

Two things a grader may probe:

  - There is no level in the formula, and no divisor. Real games divide by roughly 50 and scale by
    level; this does not. That is why hits look enormous. It is a deliberate simplification and it
    belongs on the Limitations slide, not defended as realism.
  - `max(1, ...)` means an attack that connects always does something. A resisted hit cannot do
    literally nothing.


7. WHAT THE NUMBERS ACTUALLY LOOK LIKE

The frontend scales base stats before the battle starts (usecases/singleBattleSetup.ts):

  maxHp   = baseStats.hp      * 2 + 204
  attack  = baseStats.attack  * 2 + 36
  defense = baseStats.defense * 2 + 36
  speed   = baseStats.speed   * 2 + 36

So Squirtle, base hp 44 / attack 48 / defense 65 / speed 43, enters battle as
292 HP / 132 attack / 166 defense / 122 speed, displayed as Lv100.

Worked example, verified in the running app: Squirtle uses Hydro Pump (Water, power 110) on
Charmander (base hp 39, defense 43, so 282 HP and 122 defense).

  110 * 132/122 * 1.5 (same type) * 2.0 (water into fire) = about 357

357 against 282 HP is a one-shot, and that is exactly what happened on screen: "Charmander used
Slash! Squirtle used Hydro Pump! It's super effective! Charmander fainted! You win!" with
Charmander at 0/282.

If you ever need a battle that lasts more than one hit, pick a bulkier defender. Charizard has
360 HP and 192 battle defense, which puts Hydro Pump at about 226 - it survives one and falls to
the second.


8. THE MOVE LIST IS NOT WHAT /api/pokemon RETURNS

Worth knowing because it is a trap. The battle setup does not use the backend's
`/api/pokemon/{name}` move list. The frontend fetches species data straight from PokeAPI in
services/pokedexApi.ts, and derives four "signature moves": it takes the moves the species learns
at the highest levels, looks up six of them, keeps the four strongest damaging ones, and drops
status moves because the simulator does not implement their effects.

That is why Squirtle fights with Skull Bash, Wave Crash, Hydro Pump and Headbutt, while
`/api/pokemon/squirtle` reports mega-punch, ice-punch, mega-kick and headbutt. Two different
sources. If someone asks which is authoritative for a battle: the signature-move list.

Consequence to be aware of: the setup screen needs the internet. Species data comes from
pokeapi.co, and sprites from raw.githubusercontent.com and play.pokemonshowdown.com, fetched by
the browser directly. Warming the backend's cache directory does not cover any of that.


9. HOW A TURN BECOMES TEXT - AND PULL REQUEST #37

The interactor's own message on success is the string "Turn resolved." That is a status, not
battle copy, and it used to leak onto the screen: the arena showed "Turn resolved. Arceus used
Judgment!".

The fix, in usecases/battle.ts:

  const announcement = action.type === "move" ? "" : outcome.message;

A move is narrated from its events alone, so the resolver's status string is dropped. A switch or
an item keeps its message, because "Go! Garchomp!" and "Pikachu recovered 20 HP!" are the copy.

`narrate` then builds one line from the events, in this order per event:

  "<attacker> used <move>!"
  "But it missed!"                    if it did not hit - and nothing further
  "It doesn't affect <defender>..."   if the type multiplier is 0 - and nothing further
  "A critical hit!"                   if critical
  "It's super effective!"             if multiplier > 1
  "It's not very effective..."        if multiplier < 1

and then, if the battle ended, "<opponent> fainted! You win!" or "<player> is out of usable
Pokemon!"; or if the player's active Pokemon fainted but the battle continues, "<player> fainted!
Choose another Pokemon."

Skipped actions produce no text at all, which is why a one-shot reads as a single clean sentence.

A rejection is not an error screen. The controller answers HTTP 400 with the message; battleApi
throws a BattleError; takeTurn catches it and returns the previous battle with that message in the
message box. So an illegal action costs nothing and explains itself.


10. ITEMS AND SWITCHING SHARE THE TURN RULE

Switching and using an item both cost the player their action, so the opponent still gets to
attack. That shared step is BattleSides.opponentAttacks, which exists so the rule is written once
rather than copied into three interactors.

The item refusal is worth understanding precisely, because it is the most misunderstood part of
this use case:

  - UseItemInteractor computes the effect first. If the effect is null, it returns failure with
    "It won't have any effect." - and returns the ORIGINAL bag, so nothing is consumed, and never
    calls opponentAttacks, so the turn is not spent.
  - POKEBALL and STAT_BOOST always return null: catching is not allowed in a trainer battle, and
    the simplified system has no stat stages for a booster to raise.

But you cannot show this on screen. The frontend mirrors the same rule in domain/battle.ts -
`canUseItemOn` returns false for stat-boost and pokeball - and BattleArena feeds that into the
target picker's `canSelect`, so the only valid target is disabled and the action can never be
submitted. The refusal is reachable over raw HTTP and is covered by tests; it is not reachable by
clicking. If asked to demo it, show the disabled control.


11. TWO CLIENT-SIDE DETAILS THAT SURPRISE PEOPLE

  - PP is tracked on the client. `spendPp` in usecases/battle.ts decrements it after a successful
    move; the resolver never sees PP. So a refreshed page restores full PP.
  - Every shipped route into the arena builds a party of ONE - `party: [player]` in
    createSingleBattleState. The party model and SwitchPokemon are real and tested, and the
    forced-switch path exists, but the setup screen never builds a party bigger than one. Do not
    claim switching works from the UI.

14. QUESTIONS YOU SHOULD EXPECT

Q: Why is the endpoint stateless?
A: Section 2. Name the cost as well as the benefit.

Q: Who goes first?
A: Higher Speed; a coin flip on an exact tie, and the coin is injected so it is testable.

Q: Why is the damage so large?
A: No level scaling and no divisor. A deliberate simplification, on the Limitations slide.

Q: What happens if I use a move the Pokemon does not know?
A: The interactor rejects it, the controller answers 400, and the arena shows "Player does not
   know move: X." with the battle unchanged.

Q: Can a fainted Pokemon still attack?
A: No. The interactor checks before the second attack and records a skipped action instead.

Q: Where does the type chart live?
A: entity/TypeEffectiveness.java. Multipliers multiply across a dual type, so a doubly-resisted
   move can land at 0.25 and an immunity makes the whole thing 0.

Q: Can you show an item being refused?
A: No. Section 10.

PART TWO - CODE QUALITY PROCESS
===============================================================================

1. THE SEGMENT IN ONE SENTENCE

Nothing reached main except through a reviewed pull request, and a continuous integration server
re-ran every check on a clean machine before any merge was allowed.


2. WHAT "CI" ACTUALLY MEANS

Continuous Integration. A server that runs your checks automatically so nobody has to remember to.

Concretely: .github/workflows/ci.yml tells GitHub Actions - GitHub's own build machines - what to
run. Open a pull request and GitHub starts a fresh Linux machine, clones the repository, installs
dependencies, and runs lint, tests, coverage and the build. The pull request page then shows a
green check or a red X. Nothing runs on your laptop, and nobody can forget to run the tests before
merging.

That is why it matters here: the tests are not something the team claims to run. They ran, on a
clean machine, on every pull request, and the reports are attached to the run.


3. THE TRIGGER, EXACTLY

  on:
    push:
      branches: [main]
    pull_request:

CI runs on every pull request, and on pushes to main - which in practice means after a merge. It
does NOT run when you push a feature branch.

Do not say "on every push"; a grader who opens ci.yml sees `branches: [main]` immediately. Say
"every pull request, and again on main after a merge" - which is also the better sentence, because
having thought about the post-merge run is more sophisticated than not.


4. THE TWO JOBS

Two jobs, frontend and backend, both on ubuntu-latest. Neither declares `needs:`, so they run in
parallel - a failing frontend does not stop the backend from reporting. Frontend gets Node 22;
backend gets Java 17 Temurin.

  frontend:  npm ci -> npm run lint -> npm run test:coverage -> npm run build
             -> npm audit --audit-level=high
  backend:   ./mvnw -B clean verify

What each covers:

  style                    frontend: oxlint            backend: Checkstyle, in Maven's validate
  tests with coverage      frontend: vitest, gated     backend: Surefire + JaCoCo, gated
  a production build       frontend: tsc -b &&         backend: compiles and packages the JAR
                                     vite build
  a dependency audit       frontend: npm audit         backend: nothing
  architectural rules      frontend: an import test    backend: ArchUnit, 5 tests

Two things to notice:

  - "a production build" is not only bundling. `build` is `tsc -b && vite build`, so a TypeScript
    type error fails CI even though no test asserts types.
  - The dependency audit has no backend counterpart. That is why the slide says "between them they
    cover" - "both jobs run all of these" would be false.

Both jobs upload their reports as artifacts with `if: always()`, so coverage exists especially
when the build fails.


5. THE TOOLS, IN PLAIN WORDS

  Checkstyle    A Java style checker. Reads the source and fails on violations of a written rule
                set (config/checkstyle/checkstyle.xml). Runs in Maven's `validate` phase, before
                compilation, so a style violation stops the build early. failOnViolation is true
                and includeTestSourceDirectory is true - it lints the tests too, which most
                student projects do not do.

  oxlint        The linter for the TypeScript side. Same role: catches problems by reading the
                code rather than running it.

  JaCoCo        Measures how much of the Java code the tests actually reach, and produces the
                coverage report. Also a gate - the build fails below the configured minimum.

  ArchUnit      A library for writing unit tests about architecture instead of behaviour. Our five
                tests assert which package may import which - for example that an entity never
                imports a framework.

  MockMvc       Spring's way of calling a controller without starting a real server, so a test can
                assert HTTP status and JSON shape in milliseconds.

  npm audit     Checks installed dependencies against a database of known vulnerabilities. Runs at
                --audit-level=high, so only high and critical findings fail.

The sentence that matters about all of them: none is advisory. Every one fails the build rather
than printing a warning.

4. TESTING SOMETHING RANDOM - THE PART YOU WILL BE ASKED ABOUT

Not a random seed.

The problem: a battle turn rolls dice - accuracy, a 1-in-24 critical hit, the opponent's move
choice, and the speed-tie coin flip. If the code created its own randomness, a test could not
predict the outcome, and a test that cannot predict the outcome cannot assert anything.

The solution: randomness is a constructor parameter.

  public BattleSimulator() { this(new Random()); }      // production
  public BattleSimulator(Random random) { ... }          // tests

Production gets real randomness. A test passes something that is not random at all:

  new BattleSimulator(new SequenceRandom(0.5, 0.5))

SequenceRandom is a small class in the test file extending java.util.Random, overriding
nextDouble() to return the given values in order - 0.5, then 0.5.

Why 0.5 matters: the crit check is `random.nextDouble() < 1.0/24`, and 1/24 is about 0.0417. A
returned 0.5 is not less than that, so there is definitely no crit. Pass 0.0 and you force one.
The test chooses.

The detail worth saying out loud: if the engine asks for more values than the test supplied,
SequenceRandom throws

  AssertionError("Simulator requested more random values than expected.")

So the test pins not only what each roll returns but how many rolls a turn may make. A seed cannot
do that - a seed gives a repeatable sequence, but you still have to discover what it produces, and
you cannot detect the engine quietly rolling an extra die.

The same pattern appears twice more: BooleanRandom for the speed-tie coin flip, and IndexRandom
for the opponent's move choice. And OpponentMoveSelector is an interface - a Strategy - so a test
can hand in a selector that always picks a chosen move.

If asked whether this is dependency injection: yes. The collaborator is supplied from outside
rather than constructed inside, which is what makes the seam possible.


5. WHAT IS NOT TESTED, AND WHY

The top band explicitly asks for this, so do not skip it.

  - Live PokeAPI calls. Tests use recorded JSON so the suite does not fail when the network does.
    Adapter error paths are covered; a real outage is not.
  - The dev bearer token - the string the frontend sends to say who it is. It identifies a caller
    but is not cryptographically verified, so the suite makes no security claim about it.

If pressed on the weakest number: `app`, the command-line Main, is 1.3% covered. It is a developer
entry point that prints to stdout, not a shipped path; the web layer users actually reach is 94%.
Say it before someone finds it.


6. ONE COMMAND REPRODUCES ALL OF IT

  .\scripts\verify.ps1

Runs the backend `clean verify`, then the frontend lint, coverage, build and audit. It fails below
the configured gates, so the numbers stay honest.

Practical warning on a fresh machine: it stops at the first failure under
`$ErrorActionPreference = "Stop"`, and the backend runs first, so with no Java it never reaches
the frontend at all. Java 17 Temurin has to be present.

  - Do not quote docs/testing.md for coverage. It still publishes 255 tests, 83.15% line and
