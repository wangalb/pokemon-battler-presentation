Speaker: Will

SAY:

"Our team user story is: As a Pokemon fan, I want to explore official and custom Pokemon through
battles and tournaments, so I can compare them in one app.

"The product is for someone who wants to answer a familiar question: which Pokemon would win? A
player can browse real Pokemon data, save favourites, create a Pokemon, choose competitors, play a
single battle, or run an eight-entry tournament. Accounts keep each trainer's collection separate,
and custom Pokemon can join the same battles and tournaments as official Pokemon.

"The result is one connected experience. You can discover a Pokemon, save it, compare it in battle,
then place it in a tournament. Or you can invent a Pokemon first and use it in those same workflows.
The app shows the selections, health, battle messages, winners, and final champion. That is the
product we set out to make. We will explain how it is designed later. For now, the important point
is what a player can do."

SLIDE 4 OF 30 - POKEAPI
Speaker: Aman
Target: 7:15-8:15

SAY:

"We use PokeAPI for official Pokemon data. I will show two endpoints.

"GET slash pokemon slash name-or-id gives us a Pokemon's HP, attack, defense, speed, weight, types,
move pool, and sprites. Those fields support the Pokedex, selection screens, battles, and random
tournament slots.

"GET slash move slash name-or-id gives us a move's power, type, and accuracy. Those are the values
the battle rules need when a turn is resolved.

"PokeAPI is public and requires no API key. These two requests provide the official data needed by
the user-visible features we just demonstrated."

SAY ON SLIDE 15:

Interactor is an Application Business Rule. Tournament, TournamentRound, and TournamentMatch are
Entities. The Interactor depends on interfaces owned by its use-case layer, so dependencies point

SAY ON SLIDE 16:

"TournamentMatchRunner is a Strategy. RandomBattleRunner is the production implementation, and
tests replace it with a fixed runner. RandomBattleRunner calls Albert's ResolveTurnInputBoundary,
so tournament reuses the existing single-battle rules rather than copying them. A new Battle is
created for each matchup, resetting HP, and an injected Executor lets matches in one round run in
parallel."

SLIDE 21 OF 30 - CLEAN ARCHITECTURE
Speaker: Aman
Target: 15:45-16:45

SAY:

"We can use the team user story to trace the architecture of the whole program. A player acts in a
View. A Controller translates that action into Input Data and calls an Input Boundary. An
Interactor coordinates the application rule. Entities protect rules shared across screens, such
as battle state, tournament progression, Pokemon data, and account policy. Gateways implement the
data-access interfaces owned by the use cases. Results return through an Output Boundary and
Presenter to a View Model.

"The SVG shows representative classes from all major features in those four layers. The Dependency
Rule is that source-code dependencies point inward. Five Java ArchUnit rules and three TypeScript
import rules enforce that rule in CI."


SLIDE 22 OF 30 - SOLID PRINCIPLES
Speaker: Dorothy
Target: 16:45-17:45

SAY:

"We will discuss two SOLID principles using tournament.

"First is Single Responsibility. RunTournamentRoundInteractor coordinates one round. Tournament
validates bracket progression. RandomBattleRunner simulates one match. The Presenter formats the
result. A change to bracket validity does not require a presentation change, because those classes
have different reasons to change.

"Second is Dependency Inversion. The high-level Interactor depends on TournamentMatchRunner and
repository interfaces owned by the use-case layer. RandomBattleRunner and concrete repositories
implement those abstractions outside it. This keeps framework details out of the policy and lets
tests replace production collaborators without editing the Interactor."


SLIDE 23 OF 30 - DESIGN PATTERNS
Speaker: Edison
Target: 17:45-18:45

SAY:

"One pattern our team introduced is Strategy for tournament matches. TournamentMatchRunner defines
one operation: run a matchup and return a winner. RandomBattleRunner is the production Strategy and
uses the single-battle engine. A test can inject a fixed winner Strategy instead.

"The Interactor does not ask which concrete runner it received. Because it depends on the Strategy
interface, we can add a smarter AI, a deterministic seeded runner, or another match policy without
changing tournament coordination. The same seam also makes tests fast and repeatable."


SLIDE 24 OF 30 - CODE ORGANIZATION
Speaker: Will
Target: 18:45-19:45

SAY:

"Our packaging is hybrid. At the top, backend packages represent Clean Architecture layers:
entity, use_case, interface_adapter, data_access, and app. Inside use_case, every application
action has its own package, such as resolve_turn, tournament, create_pokemon, or signup. Each action
keeps its boundary, request and response data, and Interactor together.

"The frontend uses domain, usecases, services, hooks, and components. The file tree shows both
stacks. Layer roots make dependency direction visible, while action folders make responsibilities
easy to find. Shared contracts remain in one place so features do not duplicate battle or Pokemon
policies."
