Introduction

What we built

A web app where you pick Pokémon, battle them, and run knockout tournaments — using the real stats, types, moves and sprites of every Pokémon that exists.

Real data, not made up

Every Pokémon, move and type multiplier comes from PokéAPI — 1,300+ Pokémon, their actual HP, attack, defense, speed and move pools.

Battles you play

Turn by turn: choose a move or use an item. Speed decides who strikes first; type matchups decide how much it hurts.

Tournaments that resolve

Seed eight Pokémon into a bracket and watch four quarterfinals, two semifinals and a final produce a champion.

Why this was worth building

"Who would win?" is a question every Pokémon fan has argued about and nobody can settle, because playing it out means owning the games and grinding the levels. We made the argument answerable in about fifteen seconds, and then made it repeatable eight Pokémon at a time.

  • Keep this to 45 seconds. The audience does not need the tech stack yet.
  • The "who would win" framing is what makes a non-programmer understand the point — the Specification rubric explicitly rewards that.
  • Do not say "simple" or "just a course project". Say what it does.

Specification

What the program does

A user signs in, browses every Pokémon and saves favourites to a personal library, optionally invents a Pokémon of their own, then puts any two of them into a turn-based battle, or seeds eight into a knockout bracket and watches it play down to a champion.

What a user can do

  • Create an account and sign in; some areas are reserved for trainers, admins and developers
  • Browse and search every Pokémon, and read its stats, types and moves
  • Save Pokémon to a personal library that is theirs alone
  • Invent a custom Pokémon with its own name, stats, moves and artwork
  • Fight a turn-based battle: attack or use an item
  • Run an eight-entrant knockout tournament, hand-picked or randomly filled
  • See who won, and why — damage, type effectiveness, critical hits

Deliberately out of scope

Named up front, in the blueprint, before we wrote any code:

  • Status conditions, stat stages and move-specific effects
  • Levels, EVs, IVs, abilities and held items
  • Catching Pokémon: every battle is trainer versus trainer

Note the absence

Nothing on this slide says how it works: there are no classes on it, no endpoints and no frameworks. If you have never written a line of code, you still know exactly what the app does, and that is the bar we were aiming at.

  • Say the "note the absence" point out loud. The Specification rubric's top band is literally "clearly focuses on what the program will do without mention of how it does it" and "a non-programmer can easily understand the purpose".
  • Saying we scoped things out on purpose, in advance reads as judgment. Staying quiet about them reads as failure.

Access is decided by a policy, not by a screen

backend/src/main/java/use_case/library/AddToLibraryInteractor.java
public class AddToLibraryInteractor implements AddToLibraryInputBoundary {
    private final LibraryDataAccessInterface libraryDataAccess;
    private final LibraryUserDataAccessInterface userDataAccess;
    private final LibraryAccessPolicy accessPolicy;

    // ... constructor injects all three abstractions ...

    @Override
    public AddToLibraryOutputData add(AddToLibraryInputData inputData) {
        Pokemon pokemon = inputData.getPokemon();
        if (pokemon == null || pokemon.getName().isBlank()) {
            return new AddToLibraryOutputData(false, "Pokemon name cannot be empty.",
                    LibraryFailure.INVALID_INPUT);
        }
        try {
            User requester = userDataAccess.getByUsername(inputData.getRequesterUsername());
            LibraryFailure refusal = accessPolicy.decide(requester, inputData.getOwnerUsername());
            if (refusal != null) {
                return new AddToLibraryOutputData(false,
                        "You are not allowed to modify this library.", refusal);
            }
            boolean alreadyThere = libraryDataAccess.getLibrary(inputData.getOwnerUsername()).stream()
                    .anyMatch(entry -> entry.getName().equalsIgnoreCase(pokemon.getName()));
            if (alreadyThere) {
                return new AddToLibraryOutputData(false,
                        pokemon.getName() + " is already in this library.",
                        LibraryFailure.ALREADY_PRESENT);
            }
            libraryDataAccess.saveEntry(inputData.getOwnerUsername(), pokemon);
            return new AddToLibraryOutputData(true, pokemon.getName() + " added to library.");
        } catch (UserDataAccessException exception) {
            return new AddToLibraryOutputData(false, exception.getMessage(),
                    LibraryFailure.STORAGE_ERROR);
        }
    }
}

The line that matters

The interactor never asks "is this user an admin?". It asks a LibraryAccessPolicy to decide. Change who may edit whose library and you change one class — no screen, no controller, no interactor.

  • Highlighted block is the point: policy object, not an if-chain.

Interactor & class diagram — the catalog slice, also mine

The interactor validates. It does not know what HTTP is.

backend/src/main/java/use_case/list_pokemon/ListPokemonInteractor.java
public class ListPokemonInteractor implements ListPokemonInputBoundary {
    private static final int MIN_LIMIT = 1;
    private static final int MAX_LIMIT = 100;

    private final ListPokemonDataAccessInterface dataAccess;

    public ListPokemonInteractor(ListPokemonDataAccessInterface dataAccess) {
        this.dataAccess = dataAccess;
    }

    @Override
    public ListPokemonOutputData listPokemon(ListPokemonInputData inputData) {
        int limit = inputData.getLimit();
        int offset = inputData.getOffset();

        if (limit < MIN_LIMIT || limit > MAX_LIMIT) {
            return failure("Limit must be between 1 and 100.", limit, offset,
                           QueryFailure.INVALID_INPUT);
        }
        if (offset < 0) {
            return failure("Offset must be 0 or greater.", limit, offset,
                           QueryFailure.INVALID_INPUT);
        }

        try {
            PokemonCatalogPageData page = dataAccess.listPokemon(limit, offset);
            return new ListPokemonOutputData(true, "Loaded Pokemon catalog.",
                    page.getCount(), limit, offset,
                    page.getNextOffset(), page.getPreviousOffset(),
                    page.getPokemon(), null);
        } catch (PokemonDataAccessException exception) {
            return failure(exception.getMessage(), limit, offset,
                           QueryFailure.UPSTREAM_ERROR);
        }
    }
}

Interface segregation, concretely

There is no god-object PokeApiService. There are three narrow interfaces — ListPokemonDataAccessInterface, LoadPokemonDataAccessInterface, LoadMoveDataAccessInterface, and one class quietly implements all of them. Each use case depends only on the method it actually calls.

  • Open by saying this is the catalog slice, not the custom-Pokémon one. Both are yours; this is the one with the cleanest interface-segregation story, which is why it is the code on screen. Ten seconds, then move on — do not re-explain the previous slide.
  • Highlighted lines: the only field is an interface, and the only failure path produces a domain-level enum. No ResponseEntity, no @Service, no HttpClient anywhere in this file.
  • If asked "isn't one class implementing three interfaces a smell?" — no: it is the ISP pay-off. Clients are segregated; the implementation is free to be one adapter.

public class CreatePokemonInteractor implements CreatePokemonInputBoundary {
    private final CreatePokemonOutputBoundary presenter;
    private final CustomPokemonRepository custompokemonRepository;
    private final ImageRepository imageRepository;
    private final AddToLibraryInputBoundary addToLibraryInteractor;

    // ... constructor injects all four ...

    @Override
    public void execute(CreatePokemonInputData inputData) {
        if (inputData.getName().isBlank()) {
            presenter.prepareFailView("Pokemon name cannot be empty.");
            return;
        }
        if (inputData.getHp() <= 0 || inputData.getWeight() <= 0
                || inputData.getAttack() <= 0 || inputData.getDefense() <= 0) {
            presenter.prepareFailView("Pokemon stats cannot be negative");
            return;
        }

        String spritePath = imageRepository.saveImage(inputData.getSprites());
        List<String> sprites = spritePath == null || spritePath.isBlank()
                ? List.of() : List.of(spritePath);

        Pokemon pokemon = new Pokemon(inputData.getName(), inputData.getHp(),
                inputData.getWeight(), inputData.getAttack(), inputData.getDefense(),
                inputData.getMoves(), inputData.getSpeed(), sprites, List.of());

        custompokemonRepository.savePokemon(pokemon);

        addToLibraryInteractor.add(new AddToLibraryInputData(
                inputData.getUsername(), inputData.getUsername(), pokemon));

        presenter.prepareSuccessView(new CreatePokemonOutputData(
                "Pokemon created successfully", pokemon, true));
    }
}

public class ResolveTurnInteractor implements ResolveTurnInputBoundary {
    private final BattleSimulator battleSimulator;
    private final OpponentMoveSelector opponentMoveSelector;
    private final Random tieBreaker;

    // ... constructor injects all three ...

    @Override
    public ResolveTurnOutputData resolve(ResolveTurnInputData inputData) {
        Battle battle = inputData.getBattle();
        if (battle.isComplete()) {
            return new ResolveTurnOutputData(false, null, "Battle is already complete.");
        }
        Move playerMove = battle.getPlayer().getMoves().stream()
                .filter(move -> move.getName().equalsIgnoreCase(inputData.getPlayerMoveName()))
                .findFirst().orElse(null);
        if (playerMove == null) { /* rejected with a reason */ }

        Move opponentMove = opponentMoveSelector.selectMove(battle.getOpponent());

        boolean opponentActsFirst =
                battle.getOpponent().getSpeed() > battle.getPlayer().getSpeed()
                || (battle.getOpponent().getSpeed() == battle.getPlayer().getSpeed()
                    && !tieBreaker.nextBoolean());
        // ... first/second attacker assigned from that flag ...

        List<TurnAction> actions = new ArrayList<>();
        actions.add(resolveAttack(battle, firstAttacker, firstDefender, firstMove));

        // a Pokemon that has just fainted does not get to answer
        if (battle.isComplete() || battle.isFainted(secondAttacker)) {
            actions.add(TurnAction.skipped(secondAttacker, secondDefender, secondMove));
        } else {
            actions.add(resolveAttack(battle, secondAttacker, secondDefender, secondMove));
        }

        BattleSides.sendOutNextOpponent(battle);
        return new ResolveTurnOutputData(true, new TurnResult(actions, battle), "Turn resolved.");
    }
}

What injecting Random buys

A test pins the crit roll, the accuracy roll and the opponent's choice, so every turn test is deterministic. Construct Random inside the interactor and none of that is possible. This is the single decision the whole battle test suite rests on.

backend/src/main/java/use_case/tournament/RunTournamentRoundInteractor.java
public class RunTournamentRoundInteractor implements RunTournamentRoundInputBoundary {
    private final RunTournamentRoundOutputBoundary presenter;
    private final TournamentDataAccessInterface tournamentDataAccess;
    private final TournamentPokemonDataAccessInterface pokemonDataAccess;
    private final TournamentIdGenerator idGenerator;
    private final TournamentMatchRunner matchRunner;   // Strategy
    private final Executor executor;                    // injected, not created

    @Override
    public void execute(RunTournamentRoundInputData inputData) {
        try {
            Tournament tournament = resolveTournament(inputData);
            if (tournament == null || tournament.isComplete()) return;

            List<TournamentMatch> matches = runMatches(tournament.getCurrentEntrants());
            TournamentRound round =
                    new TournamentRound(tournament.getNextRoundNumber(), matches);
            tournament.recordRound(round);        // the entity validates progression
            tournamentDataAccess.save(tournament);

            presenter.prepareSuccessView(new RunTournamentRoundOutputData(
                    tournament, round,
                    tournament.isComplete()
                            ? tournament.getChampion().getName() + " won the tournament."
                            : "Tournament round " + round.getRoundNumber() + " completed."));

        } catch (PokemonNotFoundException exception) {
            presenter.prepareFailView(exception.getMessage(), TournamentFailure.NOT_FOUND);
        } catch (PokemonDataAccessException exception) {
            presenter.prepareFailView(exception.getMessage(), TournamentFailure.UPSTREAM_ERROR);
        } catch (CompletionException | IllegalStateException exception) { /* ... */ }
    }

    private List<TournamentMatch> runMatches(List<Pokemon> entrants) {
        List<CompletableFuture<TournamentMatch>> matchTasks = new ArrayList<>();
        for (int index = 0; index < entrants.size(); index += 2) {
            matchTasks.add(CompletableFuture.supplyAsync(
                    () -> matchRunner.run(first, second), executor));
        }
        return matchTasks.stream().map(CompletableFuture::join).toList();
    }
}

Clean Architecture

How we know the Dependency Rule holds

Enforced claims, not assertions

  • Entities depend on nothing — not Spring, not Jackson, not even a use case
  • No interactor imports data_access, an adapter, or app code
  • Interface adapters touch no framework and no concrete gateway
  • Web controllers cannot reach a repository directly
  • Frontend domain/ and usecases/ import no adapter — and no localStorage

The rule is a test, not a promise

Overall design

Patterns we implemented, and why each one

Strategy

OpponentMoveSelector · TournamentMatchRunner

Move choice and match policy are pluggable. A test injects a fixed selector; production injects the random one. Swapping in a smarter AI never touches the interactor.

Caching proxy

CachedPokeApiDataAccess wraps PokeApiClient

Same interface, added behaviour: read disk first, fall through to the network, write back. No caller knows the cache exists, which is exactly the point of a proxy.

Factory method

Battle.resume(...)

Rebuilds an in-progress battle from a payload and refuses states that could not have happened — HP above maximum, negative HP, an active index outside the party. A constructor could not reject; a factory can.

Presenter + View Model

TournamentRoundPresenter → TournamentRoundViewModel

The interactor returns void and pushes output through a boundary. Formatting decisions live outside the use case, where they belong.

Ports and adapters

usecases/ports.ts + App.tsx as composition root

The pattern applied to a React app, which is unusual, most frontends let components call fetch directly. Ours cannot: the use case only sees a BattleGateway.

Immutable value object

Bag

Consuming an item returns a new bag. A rejected turn can never leave a trainer short of a Potion, a rules bug cannot become a data-loss bug.

Extensibility, as a concrete scenario

"Make the opponent play well instead of at random." Write one class implementing OpponentMoveSelector that scores each move against the defender's types, and register it in BattleApiConfiguration. Nothing else changes: not ResolveTurnInteractor, not Battle, not the controller, not the React app, not one existing test — because every one of them already depends on the interface rather than the implementation.

  • The caching proxy is the one not taught in lecture — lead with it if you want the 5/5 band, which asks for a pattern not presented in class.
  • Do not claim patterns we did not use. Six real ones beats ten name-dropped ones.

Why it is organised this way

We split the work by vertical slice, not by layer, each person carried one feature from entity to screen. Packages are named after use cases because that is how the work was actually divided, and it means a feature's files sit together instead of being scattered across four layer folders.

Accessibility

Who can use this, and who cannot

Universal Design principles we acted on

  • Perceptible information — HP is a number and a bar and a colour; effectiveness is stated in words, never colour alone
  • Tolerance for error, an item that would do nothing is refused rather than consumed, so a mistaken tap costs neither the item nor the turn
  • Low physical effort — skip link, focusable main landmark, trapped modal focus that restores on close, and prefers-reduced-motion
  • Simple and intuitive use — the menu shows only what your role can reach
  • Flexibility in use — pick entrants by hand, or let the bracket fill itself

All seven are written up in docs/accessibility-report.md.

Target users

Pokémon fans aged roughly 10 and up who want to settle a matchup argument. It assumes no prior knowledge of type charts, because the app explains every hit in plain words.

Who would struggle

A blind or severely low-vision player. Keyboard operation, focus order and dialog semantics are now real, and setup, forms and the catalog announce their state. But the battle message box is still not a live region — a screen reader user would know a turn happened and not what it did. The bracket is worse: a visual layout with no linear text equivalent.

The fix for the first is one aria-live attribute. The second is real work.

What is asserted, and what is not

Named dialogs with focus trapping, aria-pressed toggles, required/busy form semantics, and component tests for modal keyboard behaviour all landed. No screen-reader session has been run — NVDA and VoiceOver are on the manual checklist, not in CI.

  • The report exists now — docs/accessibility-report.md, all seven principles, plus a manual acceptance checklist. That was a 1/5 category and is no longer. Have the file open if a grader wants it.
  • The Excellent band needs both target users and a struggling group discussed in the presentation, using E3I terminology. This slide does both — make sure whoever speaks actually says them aloud rather than pointing at the slide.
  • Naming a real, specific failure (no live region on the battle message box, no text equivalent for the bracket) reads as far more credible than "we tried to use good contrast". Resist the urge to claim the gap is closed — it is not, and it is checkable in about ten seconds.

Limitations

What we know we did not do

Scope we chose not to model

  • No status conditions, stat stages or move-specific effects. This is exactly why stat-boost items and Full Restore are refused rather than silently ignored — the item is modelled, the effect is out of scope, and refusing costs the player neither the item nor the turn
  • Damage has no random roll and no level scaling. That simplification was in the blueprint from day one
  • Opponent AI picks a legal move at random, with no strategy behind the choice
  • Poké Balls are refused, a trainer's Pokémon cannot be caught
  • Both parties are always one Pokémon, so switching never surfaces — Battle and SwitchPokemon support it, the setup screen is what we scoped
  • PP is tracked by the client; the backend does not model it

Debt we would pay first

  1. Move accounts behind HTTP endpoints. The ports are there; what sits behind them is still the browser, so accounts do not survive a different device
  2. Point the Pokédex at our own endpoint and delete the direct PokéAPI calls
  3. Replace the dev bearer token — it identifies a caller but is not cryptographically verified
  4. Then add status conditions, which makes several already-modelled items do what their descriptions promise

Why that order

The library mirror was top of this list until last week, and paying it off deleted code rather than adding it. Same logic for what is left: converge duplicated paths first, add new surface second.

  • Say all of this ourselves, in our framing, before Q&A does it for us. A limitation you volunteer reads as judgment; the same one extracted from you reads as a gap.
  • The refused-item design is genuinely good; it is a deliberate choice, not a missing feature. Frame it that way.

Q & A

Click a question to reveal the answer. Say the first sentence, then stop and let them ask for more.

Architecture

Where does a battle rule live, and how do you stop it leaking into the controller?

In entity and use_case.battle. BattleController only translates — it rebuilds entities from the payload, calls an input boundary, and maps the result back to JSON. It never decides anything.

Why an input boundary instead of just calling the interactor?

So the controller depends on an interface it could not have written, and the interactor can be swapped or stubbed. It is what makes the controller testable with MockMvc and no battle logic in the test.

The frontend has its own domain/ and usecases/. Is that duplicated logic?

Partly, and deliberately. The frontend checks the rules a player can already see — whose Pokémon has fainted, what is in the bag, so a pointless tap costs no round trip. The backend enforces the same rules and is the authority. If they disagree, the backend wins.

Why does the frontend call PokéAPI directly when you built GET /api/pokemon?

Honestly: the Pokédex was built before that endpoint existed and we have not migrated it. So PokéAPI is reached two ways — cached through Java for battles and tournaments, directly from the browser for browsing. It is the clearest piece of technical debt we have, the endpoint and its cache are already built and tested, and the migration is confined to services/pokedexApi.ts.

What happens if the client lies about the HP it sends?

Battle.resume() rejects states that could not have happened — HP above maximum, negative HP, an active index outside the party, an HP list that does not match the party. It does not stop a determined cheater; there is no authentication on that endpoint, and for a course project we accepted that.

Is a stateless battle endpoint not just pushing state onto the client?

Yes, and that was the trade. The cost is that a refresh loses the battle. The benefit is that the API can restart mid-battle, and the tournament runs many battles without the server tracking any of them, which is why the tournament use case needed no new battle state at all.

How is the data saved? Is there a database?

There is no database. Everything is JSON — on disk on the server, or in localStorage in the browser.

Why is auth implemented twice?

It was, and we fixed half of it. The library mirror is gone — trainer libraries now have one authoritative backend store, and SyncAccount maps a browser session into an authorization projection so that access policy stayed in Java. Accounts are still local to the browser, behind ports the use cases own, which is why swapping in HTTP authentication is a composition change rather than a rewrite. Building the seam first is what made deleting the library half a small change.

What if PokéAPI is down?

Anything already in backend/cache/ still works. Anything else returns a 502 with a message. The battle itself needs no network — the client already holds both Pokémon.

Why not use a database?

None of what we store is relational or concurrent, and all data access sits behind an interface owned by a use case, so swapping in JDBC is one new class and zero changes to any use case.

Are passwords stored safely?

On the Java side: PBKDF2, 100,000 iterations, a per-user salt, and it is tested. The localStorage mirror matches those rules. Neither is a real auth system and we would not ship either one.

Testing

How do you test something random?

We inject Random, OpponentMoveSelector and the tournament Executor rather than constructing them inside interactors, so a test can pin the crit roll, the accuracy roll, the opponent's choice and the thread of execution. Every turn test is deterministic, that is the main reason the injection exists.

What is your coverage?

90.0% line on the frontend (325 tests, 77.6% branch) and 83.2% on the backend (255 tests, 68.1% branch), measured by Vitest and JaCoCo. The layer that matters most — use cases — is above 94% on both stacks. Both gates fail the build if coverage drops, and CI uploads the reports as artifacts on every run.

What is not tested?

Live PokéAPI calls — tests run against recorded JSON on purpose, because a suite that fails when someone's Wi-Fi drops is a suite people stop trusting; adapter error paths are covered instead. Also: no automated screen-reader session, no visual regression, and nothing that claims the dev bearer token resists forgery. It identifies a caller and is not cryptographically verified.

Design

You mentioned parties and switching — why didn't the demo show them?

Because the setup screen never builds a party bigger than one, so there is nothing on screen to show. The engine has it: Battle models a party, SwitchPokemon is a real use case with its own boundary, a faint triggers a forced switch, and all of it is tested. What is missing is one screen handing the interactor three Pokémon instead of one — no entity, interactor or endpoint changes. We would rather demo a path that works end to end than narrate one the UI cannot reach.

Give me one change your design makes easy that would otherwise be hard.

Making the opponent play well instead of at random. One new class implementing OpponentMoveSelector, registered in BattleApiConfiguration. Not one line changes in the interactor, the entities, the controller, the React app, or any existing test.

Is Bag being immutable not over-engineering?

It is three lines of discipline that make a class of bug impossible. Consuming an item returns a new bag, so a turn that gets rejected halfway through can never leave a trainer short of a Potion. A rules bug stays a rules bug instead of becoming a data-loss bug.

Which design pattern are you proudest of?

The caching proxy. CachedPokeApiDataAccess implements the same interfaces as the raw client and adds disk caching underneath, so no caller, not the interactor, not the controller — knows a cache exists. It also happens to be what makes the demo survive a bad connection.

Process and scope

How did you split the work?

By vertical slice, not by layer, each person took a feature from entity all the way to screen. That is why the packages are named after use cases rather than layers, and why nobody was ever blocked waiting on somebody else's layer.

What went wrong?

The frontend was built against localStorage and direct PokéAPI calls before the backend endpoints existed. It let the UI ship early, but it left us with two implementations of auth and library and two ways of reaching PokéAPI. We paid the library half back — it now has one authoritative store — and the accounts half and the Pokédex are still outstanding. If we did it again we would agree the HTTP contract first and stub the network rather than the storage.

How do you know nobody broke the dependency rule?

We do not rely on knowing. Four ArchUnit rules in Java assert that entities depend on nothing, use cases never reach a gateway or a framework, interface adapters touch neither, and web controllers cannot call a repository directly. Three equivalent import rules cover the TypeScript side, including one that keeps localStorage out of domain and use-case code. They run in CI, so a violation is a red build rather than something a reviewer has to catch.

Why did you cut the sharing user story?

Sharing a result with friends needs hosting, public URLs and a permissions story, and buys almost no design depth in return. We cut it early to put that time into the tournament runner and the role system instead, both of which had real design decisions in them.

If you had two more weeks, what would you do?

Point the Pokédex at our own endpoint and delete the direct PokéAPI calls; wire the UI to the real auth and library endpoints; then add status conditions. In that order — the first two delete duplicate code, the last adds new surface.
